# The Complete Guide to Web Application Penetration Testing (WAPT) and Application Security (AppSec)

> A comprehensive learning resource for security professionals, penetration testers, developers, DevSecOps engineers, bug bounty hunters, and anyone interested in understanding how to identify, assess, exploit safely, and remediate web application vulnerabilities.

---

## 1. Introduction

Web applications are fundamental to modern businesses. Banking platforms, e-commerce websites, healthcare systems, cloud dashboards, SaaS products, social networks, enterprise portals, and internal business applications all depend on web technologies.

As these applications become more complex, their attack surfaces grow. Modern applications commonly include:

- Browser-based frontends.
- Backend application servers.
- REST and GraphQL APIs.
- Authentication and identity providers.
- Databases and caching systems.
- Cloud infrastructure.
- Third-party integrations.
- File storage and processing services.
- Microservices and message queues.
- Mobile application interfaces.
- AI-powered features and external model integrations.

Every component introduces potential security risks.

A vulnerability in one component can affect the confidentiality, integrity, or availability of an entire application or organization.

Web Application Penetration Testing (WAPT) and Application Security (AppSec) help organizations identify, understand, prevent, and remediate these risks.

This guide covers both disciplines from foundational concepts to advanced testing and engineering practices.

### Who should use this guide?

This material is intended for:

- Ethical hackers.
- Web application penetration testers.
- Bug bounty researchers.
- Application security engineers.
- Security operations professionals.
- Software developers.
- DevSecOps engineers.
- Security architects.

11. Produce professional penetration testing reports.
12. Build a structured application security learning and improvement program.

## 2. Understanding Web Application Penetration Testing

Web Application Penetration Testing is a structured security assessment in which an authorized tester evaluates a web application for vulnerabilities that could be exploited by an attacker.

The objective is not simply to run scanners or produce a list of potential weaknesses. A professional penetration test attempts to understand how the application behaves, identify security boundaries, validate vulnerabilities, determine their impact, and provide actionable remediation guidance.

### 2.1 Primary objectives

#### Identify vulnerabilities

The tester looks for weaknesses such as:

- SQL injection.
- Cross-site scripting.
- Broken access control.
- Authentication weaknesses.
- Insecure session handling.
- Server-side request forgery.
- Insecure file upload functionality.
- Security misconfiguration.
- Sensitive information disclosure.
- Insecure API endpoints.
- Business logic flaws.

#### Evaluate exploitability

Not every security finding is equally dangerous.

A penetration tester determines whether a weakness is practically exploitable under the conditions of the assessment.

For example, a scanner may report a potentially vulnerable parameter. Manual testing is necessary to determine whether the parameter is actually interpreted by a database, reflected into a browser context, or handled safely.

#### Determine business impact

Technical vulnerabilities must be connected to their consequences.

Examples include:

- Unauthorized access to customer records.
- Exposure of confidential business information.
- Modification of financial transactions.
- Account takeover.
- Privilege escalation.
- Unauthorized administrative operations.
- Disruption of critical services.

#### Provide remediation guidance

A useful penetration test does more than identify problems. It explains how developers and system administrators can correct them.

Recommendations should address the underlying cause rather than simply hiding the observable symptom.

### 2.2 What WAPT is not

WAPT is not:

- An unrestricted attack against a production system.
- A replacement for secure software development.
- A guarantee that an application has no vulnerabilities.
- Merely an automated vulnerability scan.
- Permission to access unrelated infrastructure.
- An excuse to collect real customer information.

A penetration test is a time-bounded assessment of a defined scope. Its conclusions should clearly describe what was tested, what was not tested, and which limitations affected the results.

## 3. Understanding Application Security

Application Security is the discipline of designing, building, testing, deploying, and maintaining software so that security risks are reduced throughout its lifecycle.

WAPT is one activity within the broader AppSec discipline.

AppSec aims to make security part of the software development process instead of treating it as a final checkpoint.

### 3.1 Core AppSec disciplines

#### Secure Software Development Lifecycle

A Secure Software Development Lifecycle (Secure SDLC) incorporates security activities into every stage of software development.

| Development stage | Security activities                                                  |
| ----------------- | -------------------------------------------------------------------- |
| Requirements      | Security requirements, privacy requirements, compliance analysis     |
| Design            | Threat modeling, architecture review, trust boundary analysis        |
| Development       | Secure coding, peer review, secret management                        |
| Build             | Dependency checks, static analysis, artifact integrity               |
| Testing           | DAST, IAST, manual penetration testing                               |
| Deployment        | Hardened configuration, least privilege, secure secrets              |
| Operations        | Monitoring, patch management, incident response                      |
| Maintenance       | Vulnerability remediation, regression testing, periodic reassessment |

![Desktop View](assets/img/Web/AppSecLifecycle.jpg)

#### Threat modeling

Threat modeling identifies potential threats before an application is deployed.

It helps teams understand:

- What assets need protection?
- Who might attack the application?
- Which entry points are exposed?
- Where are the trust boundaries?
- What security controls exist?
- What could go wrong?
- How should risks be reduced?

Common approaches include STRIDE, attack trees, data flow diagrams, and misuse cases.

#### Secure coding

Secure coding means implementing software in ways that reduce common vulnerability classes.

Examples include:

- Parameterized database queries.
- Context-aware output encoding.
- Server-side authorization checks.
- Strong session management.
- Secure password hashing.
- Input validation.
- Safe file handling.
- Proper error handling.
- Secure cryptographic APIs.
- Avoiding hardcoded secrets.

#### Security testing

AppSec programs use multiple testing approaches because no single tool or technique detects every vulnerability.

##### Static Application Security Testing (SAST)

SAST analyzes source code or compiled code without requiring the application to be running.

It can identify:

- Unsafe function usage.
- Hardcoded credentials.
- Insecure cryptographic patterns.
- Potential injection flaws.
- Dangerous deserialization patterns.
- Weak input validation.

Examples: Semgrep and CodeQL.

##### Dynamic Application Security Testing (DAST)

DAST tests an application while it is running.

It sends requests to application endpoints and analyzes responses to identify possible vulnerabilities.

DAST can identify issues such as:

- Reflected input.
- Missing security headers.
- Authentication weaknesses.
- Common injection conditions.
- Exposed files and directories.
- Certain configuration weaknesses.

Examples: OWASP ZAP and Burp Suite.

##### Interactive Application Security Testing (IAST)

IAST combines application execution with security instrumentation.

It observes application behavior while tests are running and can help identify vulnerabilities with greater context about the code paths involved.

##### Software Composition Analysis (SCA)

SCA identifies third-party libraries and components used by an application.

It helps detect:

- Known vulnerable dependencies.
- Outdated packages.
- Unsupported components.
- License compliance issues.
- Risky transitive dependencies.

Examples: Dependabot, Trivy, and OWASP Dependency-Check.

##### Manual security review

Manual testing remains essential because automated tools often struggle with:

- Complex authorization rules.
- Business logic.
- Multi-step workflows.
- Context-specific trust boundaries.
- Unusual authentication flows.
- Application-specific security requirements.

### 3.2 AppSec program maturity

An organization can improve application security progressively:

1. **Reactive:** Security testing happens after vulnerabilities are discovered.
2. **Repeatable:** Standardized testing procedures are established.
3. **Integrated:** Security tools are included in development workflows.
4. **Measured:** Security risks and remediation performance are tracked.
5. **Continuous:** Security requirements, monitoring, testing, and improvement are embedded throughout the software lifecycle.

## 4. WAPT vs. AppSec

WAPT and AppSec are closely related, but they have different objectives.

| Area            | WAPT                                           | AppSec                                              |
| --------------- | ---------------------------------------------- | --------------------------------------------------- |
| Primary focus   | Identifying and validating vulnerabilities     | Preventing and managing software security risks     |
| Timing          | Usually during an assessment or release cycle  | Throughout the software lifecycle                   |
| Main activities | Reconnaissance, testing, validation, reporting | Threat modeling, secure coding, testing, governance |
| Typical users   | Penetration testers, security consultants      | Developers, security engineers, architects          |
| Output          | Penetration testing report                     | Security requirements, controls, findings, metrics  |
| Scope           | Defined application or environment             | Applications and their development lifecycle        |
| Main question   | Can this application be compromised?           | How can we build and maintain secure applications?  |

A mature security program needs both.

Penetration testing provides evidence about real-world weaknesses. AppSec uses those findings to improve architecture, development practices, and security controls.

### 5.1 Client layer

The client is usually a web browser or mobile application.

It handles:

- User interaction.
- HTML rendering.
- CSS styling.
- JavaScript execution.
- Form submission.
- Client-side validation.
- Session cookie storage.
- API communication.

Security risks include:

- Cross-site scripting.
- Insecure local storage.
- Client-side authorization assumptions.
- Sensitive information exposed in JavaScript bundles.
- Insecure browser communication.

Client-side validation is useful for usability, but it must never replace server-side validation.

### 5.2 Web server

The web server receives HTTP or HTTPS requests and may serve static content or forward requests to application services.

Common technologies include:

- Nginx.
- Apache HTTP Server.
- Microsoft IIS.
- Caddy.

Security considerations include:

- TLS configuration.
- Request parsing.
- HTTP methods.
- Reverse proxy behavior.
- Access restrictions.
- Security headers.
- Directory and file exposure.

### 5.3 Application server

The application server implements business logic and processes user requests.

Common frameworks include:

- Django.
- Flask.
- FastAPI.
- Express.js.
- NestJS.
- Spring Boot.
- ASP.NET Core.
- Laravel.
- Ruby on Rails.

Potential weaknesses include insecure input handling, broken access control, unsafe deserialization, and business logic vulnerabilities.

### 5.4 Database layer

Databases store application information.

Examples include:

- PostgreSQL.
- MySQL.
- Microsoft SQL Server.
- Oracle Database.
- MongoDB.
- Redis.

Security risks include:

- Injection.
- Excessive database permissions.
- Unencrypted sensitive data.
- Weak credentials.
- Insecure backups.
- Unrestricted database connectivity.

### 5.5 API layer

APIs allow frontend applications and other systems to interact with backend functionality.

Common styles include:

- REST.
- GraphQL.
- SOAP.
- gRPC.
- WebSockets.

APIs introduce security concerns involving authentication, authorization, object-level access, rate limiting, data exposure, and input validation.

### 5.6 Infrastructure and cloud layer

Modern applications may depend on:

- Virtual machines.
- Containers.
- Kubernetes.
- Cloud storage.
- Managed databases.
- Serverless functions.
- Identity and access management services.
- Content delivery networks.

An application can be vulnerable even when its source code is secure if its cloud resources or deployment configuration are exposed.

### 5.7 HTTP fundamentals

HTTP is the foundation of web communication.

An HTTP request typically includes:

- Method.
- URL.
- Headers.
- Optional body.

Example:

```http
GET /account/profile HTTP/1.1
Host: example.test
Accept: application/json
Cookie: session=REDACTED
```

An HTTP response contains:

- Status code.
- Response headers.
- Optional response body.

Example:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{
  "username": "alice",
  "role": "customer"
}
```

Important HTTP methods include:

| Method  | Typical purpose                                     |
| ------- | --------------------------------------------------- |
| GET     | Retrieve a resource                                 |
| POST    | Submit data or create a resource                    |
| PUT     | Replace a resource                                  |
| PATCH   | Partially update a resource                         |
| DELETE  | Delete a resource                                   |
| OPTIONS | Discover communication options                      |
| HEAD    | Retrieve response headers without the response body |

Important status code groups:

- `1xx`: Informational.
- `2xx`: Successful.
- `3xx`: Redirection.
- `4xx`: Client errors.
- `5xx`: Server errors.

A tester should understand how the application handles requests, responses, redirects, cookies, content types, and errors.

## 6. Types of Penetration Testing

| Testing Type | Description |
|---|---|
| Black-box | Tester has no internal application knowledge. |
| Gray-box | Tester receives limited access or documentation. |
| White-box | Tester receives source code, architecture, and configuration. |
| External | Assessment of publicly accessible application surfaces. |
| Internal | Assessment from an internal network position. |
| Authenticated | Testing using valid user credentials. |
| Unauthenticated | Testing without logging in. |

**Professional recommendation:** Gray-box testing with multiple user roles is particularly effective for identifying authorization and business logic vulnerabilities.

### 6.1 Black-box testing

The tester receives limited information about the application.

This resembles an external attacker who has no privileged knowledge of the internal architecture.

Advantages:

- Tests externally observable behavior.
- Helps evaluate exposed attack surfaces.
- Requires fewer internal resources.

Limitations:

- Some vulnerabilities may remain undiscovered.
- Testing can take longer.
- Internal implementation details may be unavailable.

### 6.2 Gray-box testing

The tester receives partial information, such as:

- Test accounts.
- API documentation.
- Application architecture diagrams.
- Selected source code.
- User role descriptions.

Gray-box testing often provides a practical balance between realism and coverage.

### 6.3 White-box testing

The tester receives extensive information, potentially including:

- Full source code.
- Database schemas.
- Deployment architecture.
- API specifications.
- Infrastructure configuration.
- Development documentation.

White-box testing is useful for identifying implementation flaws and tracing vulnerabilities to their root causes.

### 6.4 Authenticated and unauthenticated testing

Unauthenticated testing examines functionality available without logging in.

Authenticated testing evaluates functionality available to users with different permissions.

Both are important. Many serious vulnerabilities occur after authentication, particularly broken access control and privilege escalation.

## 8. The OWASP Top 10

The OWASP Top 10 is an awareness document that highlights important categories of web application security risk.

Always consult the current official OWASP publication when planning an assessment. The categories and wording can change between editions.

The following overview covers the major vulnerability areas commonly encountered in web application assessments.

If you want you can also see my article on [The OWASP Top 10:2025](https://anuprm.github.io/CyberBlogs/posts/OWASP-Top10-Web-Application-Security/) version.

Official reference: https://owasp.org/Top10/

### 8.1 Broken Access Control

Broken access control occurs when an application does not correctly enforce restrictions on what authenticated or unauthenticated users are allowed to do.

Examples include:

- A customer accessing another customer's order.
- A standard user accessing administrative functionality.
- A user modifying a resource owned by another account.
- A user invoking an API operation outside their assigned role.
- A user changing a protected account property.

Testing should verify authorization on the server for every sensitive operation.

### 8.2 Cryptographic Failures

Cryptographic failures occur when sensitive information is inadequately protected.

Examples include:

- Weak password hashing.
- Sensitive information transmitted without encryption.
- Insecure cryptographic algorithms.
- Hardcoded encryption keys.
- Improper certificate validation.
- Inadequate protection of stored credentials.

### 8.3 Injection

Injection vulnerabilities occur when untrusted input is interpreted as part of a command or query.

Examples include:

- SQL injection.
- NoSQL injection.
- OS command injection.
- LDAP injection.
- Template injection.
- XPath injection.

The most important defensive principle is to separate data from executable instructions.

### 8.4 Insecure Design

Insecure design involves missing or inadequate security controls at the architecture and design level.

Examples include:

- No abuse-case analysis.
- Missing transaction limits.
- Inadequate account recovery controls.
- Weak tenant isolation.
- Trusting client-side security decisions.
- Missing protection for high-risk business operations.

### 8.5 Security Misconfiguration

Examples include:

- Debug mode enabled in production.
- Exposed administrative interfaces.
- Unnecessary services.
- Default credentials.
- Overly permissive CORS.
- Verbose error messages.
- Publicly accessible backups.
- Missing security headers.

### 8.6 Vulnerable and Outdated Components

Applications depend on frameworks, libraries, plugins, and operating system packages.

Outdated or vulnerable dependencies can expose an application to known security weaknesses.

Organizations should maintain an accurate software inventory and establish a process for dependency updates and vulnerability remediation.

### 8.7 Identification and Authentication Failures

Examples include:

- Weak password policies.
- Insecure password recovery.
- Session fixation.
- Missing multi-factor authentication on sensitive accounts.
- Insecure session expiration.
- Weak account lockout or abuse protections.

### 8.8 Software and Data Integrity Failures

These failures involve insufficient verification of software or data integrity.

Examples include:

- Untrusted software updates.
- Insecure build pipelines.
- Unsigned artifacts.
- Unsafe deserialization.
- Compromised dependency sources.

### 8.9 Security Logging and Monitoring Failures

Insufficient logging and monitoring make it difficult to detect and investigate attacks.

Security events should be recorded with enough context to support investigation while avoiding unnecessary exposure of secrets and personal information.

### 8.10 Server-Side Request Forgery (SSRF)

SSRF occurs when an application can be induced to make requests to unintended destinations.

Potential targets include Internal services, Cloud metadata endpoints,  Private network resources, Internal administrative interfaces.

Defenses include strict destination validation, Destination allowlisting, Egress network restrictions, URL parsing and validation,  DNS resolution checks, Redirect restrictions, Blocking private, loopback, and link-local destinations where not needed.

**Other vulnerabilities worth mastering:**

- Broken authentication.
- Weak session management.
- Security misconfiguration.
- File upload vulnerabilities.
- Path traversal.
- Local and remote file inclusion.
- Open redirects.
- XML External Entity (XXE).
- Insecure deserialization.
- Race conditions.
- Business logic flaws.

## 9. Web Application Penetration Testing Methodology

A professional penetration test follows a repeatable process.

The exact sequence may change depending on the application, testing scope, and engagement rules.

### Phase 1: Pre-engagement, Scope Definition and authorization

Before testing begins, define:

- Written authorization.
- The target domains, subdomains and IP addresses.
- Application environments.
- In-scope API endpoints.
- Test accounts.
- User roles.
- Testing dates and hours or time windows.
- Permitted testing techniques.
- Prohibited activities.
- Rate limits and availability constraints.
- Data handling requirements.
- Emergency contacts.
- Reporting requirements or expectations.

Written authorization is essential.

The rules of engagement should state whether destructive tests, denial-of-service testing, social engineering, production testing or production payment systems, and third-party integrations are allowed.

**Deliverable:** Rules of Engagement (RoE).

### Phase 2: Reconnaissance

Reconnaissance identifies the application's attack surface.

We collects information about the authorized target.

It may include:

- Domain and subdomain discovery.
- DNS record analysis.
- Technology identification.
- Publicly exposed documentation.
- Application entry points.
- API discovery.
- Authentication mechanisms.
- Publicly exposed files.

Reconnaissance should remain within the approved scope.

#### A. Passive Reconnaissance

Collect information without directly interacting with target infrastructure.

Activities:

- Search engine discovery.
- Public DNS records.
- Certificate transparency.
- Public Git repositories.
- Public documentation.
- Technology fingerprinting.
- Public API documentation.
- Historical URL discovery.

Tools:

| Tool | Purpose |
|---|---|
| Amass | Asset discovery |
| Subfinder | Subdomain enumeration |
| crt.sh | Certificate transparency |
| SecurityTrails | DNS intelligence |
| GitHub Search | Public code discovery |
| Wayback Machine | Historical URL discovery |
| Google/Bing | Search engine reconnaissance |

#### B. Active Reconnaissance

Perform authorized interactions with the application.

Activities:

- HTTP service discovery.
- Web server fingerprinting.
- Technology identification.
- Endpoint discovery.
- Directory and file discovery.
- API endpoint discovery.
- Parameter identification.
- Authentication flow mapping.

Tools:

- Nmap.
- httpx.
- WhatWeb.
- Wappalyzer.
- Burp Suite.
- OWASP ZAP.
- ffuf.
- Gobuster.

#### C. Subdomain Enumeration

Example:

```bash
subfinder -d example.com -all -silent
```

Check discovered HTTP services:

```bash
subfinder -d example.com -silent | httpx -silent
```

Only run these commands against assets included in the authorized scope.

#### D. Technology Fingerprinting

Identify:

- Web server.
- Programming language.
- Backend framework.
- Frontend framework.
- CMS.
- CDN.
- WAF.
- Authentication provider.
- API technology.
- Database indicators.

Example:

```bash
whatweb https://example.com
```

**Deliverable:** Asset inventory and attack surface map.

### Phase 3: Application mapping and Crawling

Build a map of the application to understand it before testing vulnerabilities.

Record:

- Pages.
- Login and registration.
- Password recovery.
- User dashboards.
- Administrative interfaces and functionality.
- Endpoints.
- HTTP methods.
- Parameters.
- Request bodies.
- Cookies.
- Authentication requirements.
- User roles.
- Redirects.
- API endpoints and operations.
- Payment workflows.
- Account settings.
- File upload and download features.
- Search functionality.
- Third-party integrations.

#### Example Endpoint Inventory

| Endpoint | Method | Function | Authentication |
|---|---|---|---|
| `/login` | POST | Login | No |
| `/register` | POST | Registration | No |
| `/api/profile` | GET | Profile | Yes |
| `/api/profile` | PUT | Update profile | Yes |
| `/api/orders` | GET | List orders | Yes |
| `/api/admin/users` | GET | User administration | Admin |

Record:

- Query parameters.
- Request body fields.
- HTTP headers.
- Cookies.
- JWT tokens.
- Content types.
- User roles.
- Response codes.
- Error messages.

### Phase 4: Authentication testing

Evaluate login, registration, password reset, multi-factor authentication, account recovery, and session handling.

Authentication verifies user identity.


| Test Area | What to Investigate |
|---|---|
| Login | Weak authentication and bypasses |
| Registration | Account creation weaknesses |
| Password reset | Token predictability and reuse |
| MFA | Bypass and recovery weaknesses |
| Brute-force protection | Rate limits and lockouts |
| Account enumeration | User existence disclosure |
| Session management | Session lifecycle weaknesses |
| OAuth | Redirect and token validation |
| SSO | Identity and assertion validation |

#### JWT Security Testing

JSON Web Tokens commonly contain three components:

```text
header.payload.signature
```

Example payload:

```json
{
  "sub": "user123",
  "role": "user",
  "iat": 1794800000,
  "exp": 1794803600
}
```

Examine:

- Signature verification.
- Algorithm restrictions.
- Token expiration.
- Issuer validation.
- Audience validation.
- Key management.
- Token revocation.
- Sensitive information in claims.
- Authorization decisions based on claims.

Never assume that modifying a JWT claim grants access. The server must correctly validate the signature and enforce authorization.

### Phase 5: Authorization testing

Verify that users cannot access data or functionality outside their permissions.

Test each relevant user role and ownership boundary.

Create a role matrix:

| Function | Guest | User | Manager | Admin |
|---|---|---|---|---|
| View public pages | Yes | Yes | Yes | Yes |
| View own profile | No | Yes | Yes | Yes |

#### Major API Security Weaknesses

## 13. Authorization and Access Control Testing

Authorization determines what an authenticated user can do.

It is one of the most important areas of web application security testing.

### 13.1 Vertical privilege escalation

Vertical privilege escalation occurs when a user obtains access to functionality intended for a more privileged role.

Example:

A standard customer account is able to invoke an administrative operation.

### 13.2 Horizontal privilege escalation

Horizontal privilege escalation occurs when a user accesses another user's resources despite having the same general role.

Example:

A customer accesses an order belonging to another customer.

### 13.3 Insecure Direct Object Reference (IDOR)

An Insecure Direct Object Reference (IDOR) occurs when an application exposes a direct reference to an object but fails to enforce ownership or authorization checks.

Example:

```http
GET /api/orders/1001
```

Changing the object identifier must not allow a user to retrieve another customer's order.

The correct test is to use accounts and records created specifically for the assessment and verify server-side ownership enforcement.

### 13.4 Role-based access control (RBAC)

Role-Based Access Control (RBAC) assigns permissions to roles.

Examples:

- Customer.
- Support agent.
- Manager.
- Administrator.

A secure application should enforce permissions on the server rather than relying on hidden frontend controls.

### 13.5 Attribute-based access control (ABAC)

Attribute-Based Access Control (ABAC) evaluates attributes such as:

- User identity.
- Organization.
- Resource owner.
- Resource status.
- Transaction amount.
- Location.
- Time.
- Business context.

ABAC is useful in complex enterprise applications.

### 13.6 Authorization testing matrix

| User role     | View own records | View other records | Modify users | Admin operations |
| ------------- | ---------------: | -----------------: | -----------: | ---------------: |
| Guest         |               No |                 No |           No |               No |

| Administrator |              Yes |                Yes |          Yes |              Yes |

## 14. Injection Vulnerabilities

Injection vulnerabilities occur when untrusted input is interpreted as part of a command, query, or expression.

### 14.1 SQL injection (SQLi)

SQL injection occurs when an application constructs database queries unsafely using untrusted input.

Potential consequences include:

- Unauthorized data access.
- Data modification.
- Authentication bypass.
- Database information disclosure.
- Destruction of data in severe cases.

#### Vulnerable pattern

```python
query = "SELECT * FROM users WHERE username = '" + username + "'"
cursor.execute(query)
```

This combines data and SQL instructions.

#### Safer pattern

```python
cursor.execute(
    "SELECT * FROM users WHERE username = %s",
    (username,)
)
```

The database driver handles the value separately from the query structure.

Use the parameter placeholder syntax supported by the specific database driver.

### 14.2 NoSQL injection

NoSQL injection occurs when untrusted input affects database query operators or expressions.

Potential risks include:

- Authentication bypass.
- Unauthorized document access.
- Unexpected query behavior.

Defenses include:

- Strict input schemas.
- Type validation.
- Safe query construction.
- Avoiding direct trust in client-supplied query objects.
- Limiting database permissions.

### 14.3 OS command injection

Command injection occurs when an application passes untrusted input into operating system commands without safe handling.

Safer design generally avoids invoking a shell when a language or library API can perform the required operation.

If an external executable is necessary:

- Use a fixed executable path.
- Pass arguments as separate values.
- Avoid shell interpretation.
- Validate expected input types.
- Apply least privilege.
- Restrict the execution environment.

### 14.4 LDAP injection

LDAP injection occurs when untrusted input changes the structure of an LDAP query.

Use safe query-building methods and escape values according to the relevant LDAP context.

### 14.5 Server-side template injection

Template injection occurs when user-controlled content is interpreted as template syntax.

The impact depends on the template engine and the privileges available to the rendering process.

Do not compile or evaluate untrusted user content as a template.

### 14.6 General injection prevention

The strongest defenses include:

1. Parameterized queries.
2. Safe APIs.
3. Context-aware encoding.
4. Strict input validation.
5. Least-privilege service accounts.
6. Avoiding unnecessary command execution.
7. Secure error handling.
8. Security regression tests.

## 15. Cross-Site Scripting (XSS)

Cross-Site Scripting (XSS) occurs when untrusted content is interpreted as executable browser content.

### 15.1 Reflected XSS

Reflected XSS occurs when untrusted input is included in a response and interpreted by the browser.

### 15.2 Stored XSS

Stored XSS occurs when untrusted content is saved and later displayed to users.

Common locations include:

- User profiles.
- Comments.
- Messages.
- Product reviews.
- Support tickets.
- Uploaded metadata.

### 15.3 DOM-based XSS

DOM-based XSS occurs when client-side JavaScript processes untrusted data in an unsafe way.

### 15.4 Prevention

Defenses include:

- Context-aware output encoding.
- Safe templating frameworks.
- Avoiding unsafe DOM APIs.
- Sanitizing rich HTML with a well-maintained sanitizer.
- Content Security Policy.
- Secure handling of URLs and attributes.

Example of a risky pattern:

```javascript
element.innerHTML = userInput;
```

Safer text rendering:

```javascript
element.textContent = userInput;
```

A Content Security Policy is a defense-in-depth control. It does not replace proper output encoding.

## 16. Cross-Site Request Forgery (CSRF)

Cross-Site Request Forgery (CSRF) occurs when a browser is induced to submit an unwanted request using the victim's authenticated session.

### 16.1 Risk conditions

CSRF risk is influenced by:

- Cookie behavior.
- Authentication design.
- Request methods.
- Origin validation.
- Application workflow.
- Presence of anti-CSRF controls.

### 16.2 Defenses

Common protections include:

- Anti-CSRF tokens.
- SameSite cookies.
- Origin and Referer validation where appropriate.
- Reauthentication for sensitive actions.
- Avoiding state-changing operations through GET requests.

CSRF tokens should be unpredictable, securely bound to the user's session or request context, and validated server-side.

## 18. Server-Side Vulnerabilities

### 18.1 Server-Side Request Forgery

SSRF occurs when an application makes server-side requests based on insufficiently controlled input.

Potential targets include:

- Internal web services.
- Private network services.
- Cloud metadata endpoints.
- Local administrative interfaces.
- Other trusted services.

Defenses include:

- Destination allowlists.
- Strict URL parsing.
- DNS and address validation.
- Redirect restrictions.
- Network egress controls.
- Blocking access to sensitive internal ranges.
- Isolating request-processing components.

### 18.2 Path traversal

Path traversal occurs when user-controlled paths allow access outside an intended directory.

Defenses include:

- Canonicalizing paths.
- Using safe file APIs.
- Restricting file access to approved directories.
- Avoiding direct trust in user-supplied paths.
- Applying operating system permissions.

### 18.3 XML External Entity vulnerabilities

XXE can occur when XML parsers process external entities in unsafe configurations.

Possible consequences include unintended file access or server-side requests.

Defenses include disabling unnecessary external entity processing and using secure parser configurations.

### 18.4 Insecure deserialization

Insecure deserialization occurs when untrusted serialized data is processed unsafely.

Potential consequences vary by technology and may include unauthorized object manipulation or code execution.

Prefer simple, strictly validated data formats. Avoid deserializing untrusted objects using unsafe mechanisms.

### 18.5 Race conditions

Race conditions occur when concurrent operations interact in an unexpected order.

Examples include:

- Duplicate transactions.
- Repeated coupon redemption.
- Concurrent inventory updates.
- Account balance inconsistencies.

Defenses include database transactions, atomic operations, idempotency controls, and correct locking strategies.

- Unauthorized refunds.
- Duplicate transactions.
- Payment verification bypass.
- Workflow manipulation.
- Account balance manipulation.

### 20.1 Price manipulation

A shopping application should calculate prices on the server using trusted product and pricing data.


It should not trust client-submitted totals.

### 20.2 Coupon abuse

Test whether:

- Coupons can be reused unexpectedly.
- Expired discounts are accepted.
- Discounts can be combined incorrectly.
- Redemption limits are enforced.
- Eligibility is checked server-side.

### 20.3 Workflow bypass

Some applications require a sequence of steps.

A secure implementation should verify the current workflow state before accepting a sensitive operation.

### 20.4 Transaction replay

Sensitive operations should prevent unintended duplicate execution.

Use:

- Idempotency keys.
- Unique transaction identifiers.
- Atomic processing.
- State validation.
- Replay detection.

### 20.5 Inventory and reservation logic

Concurrent actions can create inconsistent states.

Examples include overselling inventory or booking the same limited resource multiple times.

Use appropriate database constraints, transactions, and concurrency controls.

### 21.1 Common examples

### 21.2 Security headers

Important headers include:

#### Content-Security-Policy

Restricts which content sources the browser is allowed to load and execute.

Instructs browsers to use HTTPS for a specified period.

Helps prevent MIME type sniffing.

#### Referrer-Policy

Controls the information sent in the Referer header.

#### Permissions-Policy

Controls access to certain browser features.

#### Cache-Control

Can prevent sensitive content from being stored in inappropriate caches.

Review:

- Allowed methods.
- Allowed headers.

- Preflight behavior.
- Wildcard policies.

## 27. Python Automation for Security Testing

Python is useful for automating repetitive, authorized security testing tasks.

Automation can improve consistency, speed, and evidence collection.

It should not be used to exceed the approved scope or bypass engagement restrictions.

### 27.1 HTTP request inspection

The `requests` library can be used to interact with web applications.

```python
import requests

url = "https://example.test"

response = requests.get(
    url,
    timeout=10,
    allow_redirects=True
)

print("Status:", response.status_code)
print("Final URL:", response.url)
print("Server:", response.headers.get("Server"))
print("Content-Type:", response.headers.get("Content-Type"))
```

Use a test environment or an explicitly authorized target.

### 27.2 Security header inspection

```python
import requests

url = "https://example.test"

response = requests.get(url, timeout=10)

security_headers = [
    "Strict-Transport-Security",
    "Content-Security-Policy",
    "X-Content-Type-Options",
    "Referrer-Policy",
    "Permissions-Policy"
]

for header in security_headers:
    value = response.headers.get(header)

    if value:
        print(f"[+] {header}: {value}")
    else:
        print(f"[-] Missing: {header}")
```

A missing header is not automatically a vulnerability. Evaluate it in the context of the application's architecture and threat model.

### 27.3 Basic endpoint inventory

```python
endpoints = [
    "/",
    "/login",
    "/register",
    "/account",
    "/api",
    "/api/profile",
    "/robots.txt"
]

for endpoint in endpoints:
    print(f"https://example.test{endpoint}")
```

This simple example creates an inventory. It does not make requests or assume that the paths exist.

### 27.4 Safe endpoint status checker

```python
import requests
from urllib.parse import urljoin

BASE_URL = "https://example.test"

ENDPOINTS = [
    "/",
    "/login",
    "/register",
    "/robots.txt"
]

session = requests.Session()

for endpoint in ENDPOINTS:
    url = urljoin(BASE_URL, endpoint)

    try:
        response = session.get(
            url,
            timeout=10,
            allow_redirects=False
        )

        print(
            response.status_code,
            endpoint,
            response.headers.get("Content-Type")
        )

    except requests.RequestException as error:
        print("Request failed:", endpoint, error)
```

For larger inventories, add rate limits, retries, logging, and explicit scope validation.

### 27.5 Security automation principles

Good security scripts should:

- Accept explicit target scope.
- Validate input.
- Use timeouts.
- Handle exceptions.
- Limit request rates.
- Avoid destructive behavior.
- Avoid storing credentials in source code.
- Redact sensitive data.
- Produce reproducible output.
- Record timestamps and test context.

## 30. Vulnerability Validation and Risk Assessment

A professional assessment distinguishes confirmed vulnerabilities from observations and potential weaknesses.

### 30.1 Finding validation

For each suspected vulnerability:

1. Identify the affected component.
2. Reproduce the behavior.
3. Establish the relevant security boundary.
4. Confirm the expected behavior.
5. Confirm the observed behavior.
6. Determine whether the behavior is exploitable.
7. Assess the impact.
8. Preserve minimal evidence.
9. Recommend a root-cause fix.

### 30.2 Severity assessment

A common severity model uses four or five levels.

| Severity      | General meaning                                                          |
| ------------- | ------------------------------------------------------------------------ |
| Critical      | Severe compromise or broad high-impact exposure                          |
| High          | Significant security impact with practical exploitability                |
| Medium        | Meaningful but more limited risk                                         |
| Low           | Limited security impact                                                  |
| Informational | Observation or improvement opportunity without a confirmed vulnerability |

Severity should reflect both technical and business context.

### 30.3 CVSS - Vulnerability Severity and Risk Assessment

The Common Vulnerability Scoring System (CVSS) provides a standardized approach to assessing vulnerability severity.

| CVSS Score | Severity |
|---|---|
| 0.0 | None |
| 0.1–3.9 | Low |
| 4.0–6.9 | Medium |
| 7.0–8.9 | High |
| 9.0–10.0 | Critical |

Important factors include:

- Attack vector.
- Attack complexity.
- Privileges required.
- User interaction.
- Scope.
- Confidentiality impact.
- Integrity impact.
- Availability impact.

A CVSS score should not replace an explanation of business risk.

#### Example Severity Classification

| Vulnerability | Possible Severity |
|---|---|
| Unauthenticated remote code execution | Critical |
| Administrative account takeover | Critical |
| Cross-user sensitive data access | High |
| Stored XSS affecting administrators | High |
| Limited information disclosure | Low |
| Missing security header | Informational/Low |

Actual severity depends on exploitability, impact, privileges, exposure, and business context.

#### Business Risk Assessment

Consider:

- Confidentiality.
- Integrity.
- Availability.
- Financial loss.
- Regulatory implications.
- Customer impact.
- Operational disruption.
- Attack complexity.
- Existing compensating controls.

---

### 30.4 Risk prioritization

Organizations should consider:

- Internet exposure.
- Asset criticality.
- Data sensitivity.
- Exploitability.
- Existing mitigations.
- Business impact.
- Threat intelligence.
- Regulatory obligations.

A medium technical vulnerability affecting a critical financial workflow may require more urgent attention than its score alone suggests.

## 31. Professional Penetration Testing Reporting

A penetration testing report is one of the most important deliverables of an engagement.

It should be clear to both technical and nontechnical readers.

### 31.1 Executive summary

Include:

- Purpose of the assessment.
- Scope.
- High-level methodology.
- Overall security posture.
- Most significant risks.
- Recommended priorities.

Avoid excessive technical detail in this section.

### 31.2 Scope and limitations

Document:

- Tested domains.
- Tested applications.
- API endpoints.
- User roles.
- Testing dates.
- Excluded systems.
- Testing restrictions.
- Environmental limitations.

### 31.3 Finding structure

Each finding should contain:

#### Finding title

A concise description of the weakness.

#### Severity

Critical, High, Medium, Low, or Informational.

#### Affected asset

The affected application, endpoint, or component.

#### Description

Explain the underlying security issue.

#### Evidence

Provide relevant requests, responses, screenshots, or logs.

Redact secrets, personal information, and unrelated customer data.

#### Impact

Explain what an attacker could achieve and why it matters.

#### Reproduction steps

Provide enough detail for the authorized recipient to reproduce the finding safely.

#### Root cause

Explain the implementation or configuration weakness.

#### Remediation

Provide specific corrective actions.

#### References

Include relevant OWASP, CWE, CVE, vendor, or standards references where appropriate.

### 31.4 Example finding template

```markdown
#### Finding: Broken Object Level Authorization

**Severity:** High

**Affected component:** Customer Orders API

**Description:**

The application does not consistently enforce resource ownership
when retrieving order information.

**Impact:**

An authenticated user may be able to access order information
belonging to another customer.

**Evidence:**

Use two authorized test accounts with test records.
Document the request and response demonstrating the
authorization failure.

**Root cause:**

The backend retrieves an order using its identifier without
consistently verifying ownership.

**Remediation:**

Enforce authorization checks on the server for every object
access. Derive the authenticated user identity from trusted
session or token context and verify resource ownership before
returning the object.

**Retest:**

Verify that each test account can access only its authorized
records.
```

### 31.5 Remediation verification

A retest should determine whether:

- The original weakness is fixed.
- The fix works across relevant user roles.
- Related endpoints are also protected.
- The change has not introduced a regression.
- Security logging and monitoring remain effective.

### Module 01 — Web Architecture and HTTP Fundamentals

#### Objective

A tester who does not understand how requests, responses, sessions, and application components work will struggle to distinguish normal behavior from security weaknesses.

#### Learning objectives

- Describe how browsers communicate with web servers.

#### Topics

**1. Client-server architecture**

### Module 05 — Authorization and Access Control

#### Objective

Learn to identify weaknesses in how an application determines what authenticated users are permitted to access.

Authorization failures are especially important because they can expose sensitive records or administrative functionality without requiring an attacker to defeat authentication.

#### Learning objectives

- Understand authentication versus authorization.
- Understand RBAC and ABAC.
- Identify horizontal privilege escalation.
- Identify vertical privilege escalation.
- Understand IDOR and BOLA.
- Test ownership enforcement.
- Evaluate API authorization.
- Build authorization test matrices.

#### Topics

**1. Authorization fundamentals**

Understand why successful authentication does not imply permission to perform every operation.

**2. Role-based access control**

Study role and permission relationships.

**3. Attribute-based access control**

Understand policy decisions based on user, resource, and contextual attributes.

**4. Horizontal privilege escalation**

Understand access to resources belonging to another user.

**5. Vertical privilege escalation**

Understand access to functionality reserved for a higher-privilege role.

**6. IDOR and BOLA**

Study how object references and missing ownership checks can expose data.

**7. Tenant isolation**

Understand authorization boundaries in multi-tenant applications.

**8. Server-side enforcement**

Learn why authorization decisions must be enforced by trusted backend components.

#### Practical exercises

Use two or more test accounts with synthetic records.

- Create an authorization matrix.
- Verify that each user can access their own records.
- Verify that users cannot access another account's records.
- Compare access across roles.
- Test whether sensitive API operations enforce the expected permissions.
- Document the expected and observed behavior.

#### Expected outcome

You should be able to systematically assess authorization boundaries across an application's users, roles, objects, and API operations.

#### Completion checklist

## 39. Conclusion

Web Application Penetration Testing and Application Security are complementary disciplines.

WAPT helps identify and validate weaknesses in deployed applications. AppSec helps prevent those weaknesses through secure architecture, development practices, testing, and continuous improvement.

A strong web application security professional needs more than knowledge of vulnerability names or familiarity with automated tools.

The most valuable skills include:

- Understanding web architecture.
- Reading and interpreting HTTP traffic.
- Mapping application functionality.
- Identifying trust boundaries.
- Testing authentication and authorization.
- Understanding application-specific business logic.
- Assessing APIs and modern identity protocols.
- Reviewing source code.
- Automating repetitive tasks safely.
- Communicating risk clearly.
- Recommending practical remediation.
- Understanding legal and ethical boundaries.

The 12-module Web Application Security Masterclass in this guide provides a structured path for developing these skills.

The best way to learn is through a combination of theory, controlled practical exercises, source code review, documentation, and repeated testing.

Security is not a one-time activity. Applications change, dependencies evolve, infrastructure expands, and new threats emerge. Effective application security requires continuous learning, assessment, remediation, and improvement.

> **Learn the technology. Understand the trust boundaries. Test methodically. Validate carefully. Remediate at the root cause. Always work with authorization.**
